# Tirzepatide Log: project context

Single-file web app (`index.html`): HTML, CSS and vanilla JS in one file. Live at https://archie-hub.github.io/tirzepatide-log/. Also served (unlisted, noindex) by the phoe.be CloudFront distribution at https://www.phoe.be/tirzepatide-log/ (the phoe.be menus link there; the old wrapper page `/tirzepatide-log.html` was removed on 2026-10-06). Since 2026-10-06 the phoe.be CloudFront (`EWVXJSS4UKRDN`) serves `/tirzepatide-log/*` from S3 first (`s3://www.phoe.be/tirzepatide-log/`, files copied by `publish-s3.sh`, `/tirzepatide-log/` mapped to `index.html` by the CloudFront Function `tirzlog-directory-index`) through the origin group `tirz-s3-then-github`, which falls back to GitHub Pages on 403/404/5xx, so a GitHub outage no longer affects phoe.be or doctor links (`AJC_DATA.csv` is deliberately not in S3, so it still comes from GitHub). Rewind: `~/apps.d/tirzepatide-cloud/rewind/cloudfront-before-after.sh rewind`. The phoe.be Terraform (`~/phoe.be/infrastructure/cloudfront.tf`, on origin/main; pull first, a stale clone once made me think otherwise) defines the GitHub Pages origin and the `/tirzepatide-log/*` and `/saa-c03-practice/*` behaviors but not the S3-first origin group, the function or the removed origin request policy, so a `terraform apply` there would quietly put `/tirzepatide-log/*` back on GitHub Pages only; add the group and function to it first. Optional PWA files beside it: `manifest.webmanifest`, `sw.js` (network-first cache), `icons/`, `og-image.png` (link preview); `index.html` only loads the manifest/service worker over http(s). No build step, no dependencies. Network calls: a same-origin fetch of `AJC_DATA.csv` when hosted and the browser log is empty (`loadHostedData()`), and the optional invite-only cloud sync below (only after the visitor signs in). Must keep working when opened straight from disk (`file://`) and when hosted statically (GitHub Pages, S3 + CloudFront). `package.json`/`tests/` are dev-only tooling (Playwright smoke tests via `npm test`) and don't affect the app's zero-dependency runtime.

## What it does
- Logs date, dose (mg), weight (lbs), comments, calories, food notes, glucose (mg/dL), injection site, blood pressure (systolic and diastolic, mmHg; fields `sys`/`dia`, a reading needs both), waist (`waist`, inches), body fat (`fat`, %) and muscle mass (`muscle`, lbs).
- Progress maths block (pure functions, "progress maths" in `index.html`): `progressInfo()` (percent of start weight lost, week on treatment counted from the first entry with a dose, milestones at 5/10/15/20/25 % as the first weigh-in at or below the target, weight lost at week 12 = nearest weigh-in within 7 days of day 84), `rollingRates()`/`slopeUpTo()` (4-week least-squares pace), `fastLoss()` (informational notice when losing more than 1 % of body weight a week, `FAST_PCT`), `weeklyAverages()`/`bestWeek()`, `extremes()`, `thisVsLast()`, `consistency()` (streak, average and longest gap, % of last 30/90 days), `injectionPattern()` (weight vs its centred 7-day mean by days since the injection weekday; needs about 4 weeks). `settings.baseline` (optional start weight before treatment, set in the settings dialog) replaces the first weigh-in as the base for percentages, milestones and the goal ring.
- There is no separate Progress panel (it was removed). Percent lost and the week on treatment show on the Change card's sub line; milestones, lost at week 12 and the body measures (waist with waist-to-height, body fat, muscle) appear in the doctor report, and waist also has its own chart tab and table column. A fast-loss notice (`#fastNote`) sits under the plateau notice. "More insights" (`#insightsPanel`, a minimised `<details class="fold">` directly below the chart) holds this week vs last, highest/lowest, best week, 4-week pace, logging streak, weigh-in consistency, milestones, lost at week 12, the 30/90-day forecast at the 28-day pace (`recentSlope()`), the by-injection-day bars and a weekly averages table (last 12 weeks).
- Plateau notice under the top row (`plateauInfo()`): 4+ weigh-ins over at least 18 days within the last 21, net trend of 1 lb or less over 3 weeks and a spread of 4 lbs or less. Also a "Weight trend" box and summary line in the report.
- Top row (stats): latest weight, goal (ring + projection from a 28-day least-squares slope; Set a goal / Edit open the settings dialog), change since start, latest fasting glucose. Below it, the plan row, built from the same `.stat` cards so it is exactly as tall as the top row: Current dose (with week and start date), Next dose (weekday from settings, else last logged site date, else current dose start; a 7-segment strip along the bottom whose filled segments warm from green to red as the dose day nears; Change link), a `.stack-box`/`.stack` slot holding two small panels (Days covered, and Latest BP coloured by category once any BP is logged; Days covered alone keeps a full panel otherwise): near-square side-by-side tiles when the slot is 220px or wider, compact stacked strips below that (container query on `.stack-box`), and BMI. There is no Backup card; the only export buttons are the bottom button row's Export CSV and the backup line's link (`lastExport` is still recorded by `markBackedUp()`).
- "Results by dose" panel: lbs/week per dose segment (also in the doctor report).
- BMI card (plan cards, next to Next dose): until a height is saved it shows one text field (accepts `5'9"`, `5 9`, `69 in`, `175 cm`; saves on Enter/blur, no button); afterwards BMI is calculated automatically from the latest weigh-in. Height is stored in inches as `settings.heightIn` and edited from the card's Edit link (settings dialog). The card shows the stage name and distance to the next stage on the left (✎ edits the height) and a gauge ring on the right with the BMI value inside it (270° arc, BMI 15 to 45, stage-coloured segments, marker at the current BMI; smaller in narrow cards via a container query); hovering/focusing/tapping a segment describes that stage, and hovering/focusing/tapping the BMI number pops up a bubble with four rows (Latest, Start, Next, Pace; the report keeps the full sentence from `bmiNextText()`); hovering, focusing (keyboard) or tapping a coloured segment pops up a bubble above the ring with that stage's BMI and weight range (nothing is reserved for it when idle). Stages (`BMI_STAGES`): underweight blue, normal green, overweight amber, obesity I orange, II deep orange, III red; the rounded value decides.
- Stats cards, tabbed charts (weight / BMI / glucose / Pace / Waist / blood pressure / calories; Pace = rolling 4-week lbs/week with a zero line and the fast-loss line, orange dots above it; Waist has a dashed half-height line when a height is saved; the BMI tab only shows once a height is saved, dots coloured by BMI stage with dashed stage threshold lines) with dose bands, 7-day average line, hover tooltip, range switch (All, 6 mo, 3 mo, 30 d).
- Combined chart tab (`buildCompare()`, `COMPARE_SERIES`): pick any of weight, BMI (needs height), glucose, systolic, diastolic, waist, body fat, muscle, calories with the chips above the chart (saved in `settings.compare`, default weight/glucose/systolic). Each line is min-max scaled to its own range in view (shape, not size), dots are daily values, lines are 7-day averages; the tooltip shows real values. Optional in the doctor report (`rcCompare`, off by default) with the line names drawn inside the image.
- Settings dialog also has "Add weekly dose reminder to calendar (.ics)" (`#sIcs`, weekly RRULE on the injection day), the web counterpart of the iOS dose-reminder notification.
- The Import data / Doctor report / Export CSV / Clear all data buttons (and Install app when offered) are a `.page-bar` row below the Add entry panel, not in the header.
- Header backup line (`renderBackup()`): last export age, amber when never exported or older than 14 days with changes since; links to Export CSV. Delete has no confirm; a toast offers Undo for 8 s (`showUndo()`).
- The Entries and Add entry panels are `<details class="fold">` and start minimised (header with chevron, entry count and Show/Hide); clicking Edit on a row opens the form panel. Tests open them with `expandPanels()`.
- Entry table with edit/delete and dose-colored rows. Paged, 5 per page, newest first (Previous / numbered pages / Next).
- Import wizard: file, drag and drop, or pasted CSV; auto-matches columns, handles `MM/DD/YYYY` vs `DD/MM/YYYY`, converts kg to lbs, merge or replace by date.
- Export CSV in the exact 13-column format below.
- "Doctor report": date-range report with summary boxes, charts, fasting glucose ranges (counts and share per ADA range), blood pressure categories (counts and share per AHA category), optional BP chart, an Avg BP column in the dose schedule and a BP column in the full log, dose schedule, comments table, optional full log. Mirrors the dashboard (keep it that way: anything added to the dashboard also goes in the report): boxes for dose, weight, change, goal progress and projection, BMI (first to last, with stage), BMI next stage, latest and average fasting glucose, latest and average blood pressure, entries and days covered, next dose, plus (period-based) weight lost %, weeks on treatment, milestones, lost at week 12, 4-week pace with the fast-loss wording, highest/lowest, best week, weigh-in consistency, waist (with waist-to-height), body fat and muscle mass; optional extra charts for loss pace and waist, an optional weekly averages table (both off by default), and the by-injection-day sentence in the text summary only; optional BMI chart plus a BMI stage table (the checkbox is always listed but disabled with a hint until a height is saved); all of it also in the text summary. Output via print/PDF, PNG chart images, copied text summary, mailto, Web Share, CSV for the range.

## Landing page and sign-in gate
On the hosted site (http/https) the app shows only the landing page (`#landing`: marketing copy, sample screenshots from `landing/*.jpg` made by `node tests/make-landing-shots.js` from the fake sample year, Sign in button, "Request an invite" mailto to info@phoe.be) until someone is signed in; no graph, entry or setting is visible, and the hosted data file is not fetched. The gate is `applyGate()` plus a tiny script in `<head>` that sets `html.landing` before first paint (so there is no flash of the dashboard); `main > *` except the landing and `#msg` are hidden by CSS under it. It is a view gate, not encryption: the log still sits in this browser's `localStorage` (and stays there after sign-out). Not gated: `file://`, and doctor links (`#share=<token>`). The old `#cloud` URL flag is gone.  Tests: the "landing:" and "hosted and signed out" cases in `tests/cloud.spec.js`.

## Cloud sync (optional, invite only)
Phase 2 of `docs/aws-sync-plan.md`; the backend is the private `tirzepatide-cloud` repo (`~/apps.d/tirzepatide-cloud`, Cognito + HTTP API + Lambda + DynamoDB, API contract in its README and `lambda_src/handler.py`). Code is the "cloud sync" block in `index.html` (`cloudSignIn()`, `syncNow()`, `syncDetect()`, `CLOUD` holds the public ids). Behaviour:
- Sign-in is the landing page's button (the Settings section `#cloudBox` with Sync now, Sign out and doctor links only shows once signed in; never on `file://` or without `crypto.subtle`; `#cloudOpen` in the button row opens it). Sign-up is disabled on the Cognito pool; only invited accounts work.
- Sign-in is authorization code + PKCE against the Cognito hosted login; tokens and sync bookkeeping live under `localStorage` key `tirzepatide-sync` (`sw.js` never caches the `?code=` redirect). Sign out keeps local data. Clear all data signs out first so it cannot delete the cloud copy.
- Sync is automatic: on page load, 1.5 s after any save (debounced), when the tab is hidden (pushed at once, `keepalive`), when the tab comes back (after 5 s) and when the connection returns; Sync now is only a manual retry. Per-day last-write-wins on a client `updatedAt`; edits are found by diffing each day against what the server last had (`syncDetect()`), so edit code needs no sync calls. Deletes are tombstones. Synced settings: goal, baseline, heightIn, units, doseDay, compare (never the report name). Fields sent: the 13 CSV fields in lbs/inches, in the API's names (`toCloud()`/`fromCloud()`; add a field in both, in the Lambda whitelist, and in the iOS app).
- First sync on a device keeps the pre-sync log under `tirzepatide-log-v1-before-sync`; a log pre-loaded from `AJC_DATA.csv` asks before it is uploaded (`settings.hostedLoaded`). The server refuses a single out-of-range day without blocking the rest (shown as "N days were not synced").
- Tests: `tests/cloud.spec.js` serves the page at `http://localhost:8080/` and fakes Cognito and the API in memory. A live check against the real stack was run by creating a throwaway user (see the cloud repo's `scripts/smoke_test.py`).
- Doctor links (Phase 4): when signed in, the Cloud sync section has "Doctor link" (create with or without notes, Copy link, Revoke; `shareUrl()`, `refreshShares()`). A link is `<app url>#share=<43 char token>`; opening it runs `loadShare()`: a read-only copy of the page (`body.share` hides every editing control) fed by the public `GET /share/{token}` route. In that mode `SHARE_TOKEN` makes `load()/save()/loadSettings()/saveSettings()/loadSync()` and the report-name storage no-ops, so nothing is read from or written to the doctor's own browser data, even if they use the app themselves. The token is in the fragment so it is never sent to a server or logged; links never expire, but the patient can revoke them and they stop when the owner's access is removed. Notes (comments, food notes) only travel if the patient ticked the box. `topHash()` also reads the hash of the page that embeds the app. Tests: the "owner" and "doctor" cases in `tests/cloud.spec.js`.
- A **Sign out** button sits in the page header whenever signed in (also in the Settings dialog). The iPhone app has no exports at all (see its CLAUDE.md); the web app keeps CSV export and the doctor report.
- iOS has the same sync (Phase 3, `Support/Cloud/` in the iOS repo). Keep the two engines and their tests in step; the iOS redirect URI `tirztrack://auth` is in the Cognito callback list.

## Data and privacy rules
- All data lives in the visitor's browser (and, only for an invited signed-in account, in that account's cloud copy) (`localStorage` key `tirzepatide-log-v1`; report name under `tirzepatide-report-name`; goal, baseline weight, dose day, height, units, combined-chart choice and backup timestamps under `tirzepatide-settings`). Never add code that uploads data except through the cloud sync above.
- Never commit real health data. `.gitignore` excludes `*.csv` except `sample-data/`. The sample file is fake.
- Every localStorage call is wrapped in try/catch; the app must render with empty storage.

## Units
All data is stored and exported in lbs and inches. `settings.units` (`'us'` default, `'metric'`, `'uk'`) only changes display and typing: use `dw()`/`fw()`/`WU()`/`toLbs()` for weights, `fmtHeight()` for height, `.wu` spans for unit labels in static HTML. Metric shows kg and cm everywhere, including the report and charts; CSV export stays in lbs. Never show a raw stored weight.

UK units (`'uk'`): absolute body weights show as stones and pounds (`stLb()`, `fwu()`, `fwa()`, `fwuTrim()`, `fwFloor()`, headers via `WUA()`/`.wua` spans = "st lb", chart axis in decimal stones via `WUC()`), while changes, rates and "to go" amounts stay in pounds (so `dw()`/`fw()`/`WU()` behave as US there). Weight, goal and start weight fields become text fields accepting `13 5.2`, `13 st 5 lb`, `12.5` (under 40 = stones) or `185 lbs` (`parseStLb()`/`readW()`). Waist is stored in inches and shown in cm when metric (`flen()`/`LU()`/`.lu`); muscle mass is stored in lbs. When adding a new weight display decide whether it is absolute (use `fwu`/`fwa`) or a difference (use `fw`/`dw` + `WU()`).

## CSV format
`Date,Dosage (mg),Weight (lbs),Comments,Calories,Food Notes,Blood Sugar (mg/dL),Injection Site,Systolic (mmHg),Diastolic (mmHg),Waist (in),Body Fat (%),Muscle Mass (lbs)` (later columns were added over time; 7-, 8- and 10-column files still import; the import wizard auto-maps columns whose names contain "waist", "fat"/"body fat", "muscle"/"lean") with ISO dates, CRLF line endings, quoted fields where needed. Comments can contain newlines and commas. Blank cells are valid.

## Design decisions
- Dose colors: 2.5 blue, 5 green, 7.5 yellow, 10 orange, 12.5 pink, 15 violet (`doseColor()`).
- Metric colors: weight teal `#0ea5a4`, glucose orange `#f97316`, calories violet `#8b5cf6`.
- Glucose readings are always fasting. Values are coloured by ADA fasting range (`sugarZone()`): below 100 green `#16a34a`, 100-125 prediabetes amber `#d97706`, 126+ diabetes red `#dc2626` (rounded value decides). Applied to the stat card, entries table, chart dots (with dashed 100/126 threshold lines; the sugar 7-day line is neutral slate so it isn't confused with amber), tooltip, and doctor report.
- Blood pressure (`bpZone(sys, dia)`, AHA categories, the higher number decides, rounded values): Normal below 120 and below 80 green `#16a34a`, Elevated 120-129 and below 80 amber `#d4a106`, Stage 1 130-139 or 80-89 orange `#f97316`, Stage 2 140+ or 90+ red `#dc2626`. No hypertensive-crisis tier. The BP chart plots one bar per reading from diastolic (hollow dot) to systolic (solid dot), coloured by category, with dashed top (120/130/140) and bottom (80/90) limit lines and grey 7-day average lines. Applied to the stat card, entries table, chart, tooltip and doctor report. Import auto-maps columns containing "systol"/"diastol"; a combined "Blood pressure" column (`120/80`) also imports. The entry form has a single field typed as `119/79` (`parseBp()`); storage and CSV keep two numbers.
- Light and dark mode via CSS variables; `prefers-reduced-motion` respected. Report content is always light (print-safe).
- No external fonts or scripts, so it works offline.

## How it was tested
Automated: `npm test` runs `tests/smoke.spec.js` (Playwright, Chromium) — imports `sample-data/TirzepatideLog-sample-year.csv`, checks stats and charts render, hover tooltip, report preview, CSV/PNG downloads, print-to-PDF with `.report-mode`, and a 390px-wide dark-mode render with no horizontal overflow. The progress/insights/body/UK-unit tests use hand-built CSVs with figures worked out by hand (steady 0.5 lb/day loss, a 200 to 175 lb log with known milestone weeks), so a failing number means the maths changed, not the sample data. Run it after changes to these areas; extend the spec file rather than only checking by hand.
Manual: headless Chromium screenshots for anything the spec doesn't cover yet (visual/layout changes, new UI).
